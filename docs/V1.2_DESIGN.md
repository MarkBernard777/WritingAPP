## 2. Canonical hierarchy and ownership

```
Book (Project)
 └── Part*          (optional grouping; 0..n)
      └── Chapter   (owns RelativeMarkdownPath UTF-8 file)
           └── Scene*  (canonical outline + prose association; 0..n)
```

| Level | Identity | Owns | Does not own |
|-------|----------|------|--------------|
| **Book** | `Project.Id` + portable root | DB file, folder tree, settings for that book | App install dir / LocalAppData content |
| **Part** | `Part.Id` | Title, sequence within book; groups chapters | Markdown prose |
| **Chapter** | `Chapter.Id` | Title, sequence, **one** UTF-8 Markdown file path, content hash / chapter word count | Scene outline fields |
| **Scene** | `Scene.Id` (**single** inventory row) | Outline metadata, chapter assignment, sequence within chapter (or unassigned), optional prose span association, scene word count | A second DB table or DocumentField duplicate |

**Ownership rules**

1. **Project** is the Book. No separate Book table.
2. **Part** is optional. Existing projects migrate with `Chapter.PartId = null` (implicit “Ungrouped” bucket). Creating parts never requires rewriting chapter Markdown.
3. **Chapter** remains the unit of compile/export concatenation order: Part sequence → Chapter sequence (ungrouped chapters after all parts, preserving today’s sequence numbers).
4. **Scene** remains one canonical record projected into Story Data, Documents Scene List, corkboard, and Manuscript. Editing in any surface updates the same row.
5. Unassigned scenes (`ChapterId == null`) are first-class for planning; they have no chapter prose span until assigned.

## 3. Ordering invariants and delete / move behaviour

### Ordering invariants

| Level | Order key | Uniqueness | Notes |
|-------|-----------|------------|-------|
| Part | `Part.SequenceNumber` | Unique `(ProjectId, SequenceNumber)` | Dense 1..n after renumber |
| Chapter | `Chapter.SequenceNumber` | Unique `(ProjectId, SequenceNumber)` **global within book** | Compile order = sort by Part sequence (null Part last), then Chapter sequence |
| Scene (assigned) | `Scene.SequenceNumber` | Unique `(ChapterId, SequenceNumber)` when `ChapterId` not null | Replaces today’s project-wide unique scene sequence for assigned scenes |
| Scene (unassigned) | `Scene.SequenceNumber` | Unique among unassigned in project: treat as `(ProjectId, ChapterId IS NULL, SequenceNumber)` | Planning backlog order |

`NextSceneId` remains an optional narrative link, not the primary sort key. UI may offer “link next” but reorder commands update `SequenceNumber`.

### Delete behaviour

| Delete | Behaviour |
|--------|-----------|
| **Part** | Chapters in that part become `PartId = null` (ungrouped). No chapter file deletion. Confirm if part is non-empty. |
| **Chapter** | Confirm. Unlink scenes (`ChapterId = null`, renumber unassigned). Delete Markdown file after DB commit succeeds (same spirit as today). Renumber remaining chapters. Remove scene span markers from deleted file only (file gone). |
| **Scene** | Confirm. Remove DB row; if chapter Markdown contains that scene’s delimiters, rewrite file to unwrap markers and keep prose (do not silently delete author prose). Clear `NextSceneId` references pointing at it. |

### Move behaviour

| Move | Behaviour |
|------|-----------|
| Part Up/Down / DnD | Swap/renumber part sequences in one SQLite transaction |
| Chapter between parts | Update `PartId`; keep global `SequenceNumber` unless DnD supplies a new index (then renumber) |
| Chapter Up/Down within book | Existing temp-negative swap pattern (or equivalent) in one transaction; filenames stay stable |
| Scene between chapters | Update `ChapterId`; renumber source and destination chapter sequences; **move prose span** in Markdown when both chapters have files (see §5–6) |
| Scene within chapter | Renumber only; Markdown delimiter order should match sequence after operation (rewrite once) |

All reorder operations must be keyboard-accessible (Up/Down or equivalent) in addition to drag-and-drop.

## 4. Canonical Scene — no duplicate stores

**Confirmed design rule (roadmap):** *No information should need to be entered twice.*

| Surface | Role |
|---------|------|
| Story Data → Scenes | Full outline editor on `Scene` |
| Documents → Scene List | Read/projection (+ light edits if already supported) of same `Scene` rows |
| Manuscript sidebar / corkboard | Same `Scene` rows filtered/sorted |
| Working document “Scene List” template notes | May hold free-form notes; **must not** become a second scene inventory |

**Forbidden in v1.2**

- A second `SceneBodies` / document-field scene table as system of record.
- Copying scene title/status into DocumentFields as the inventory.
- Divergent “corkboard-only” entities.

Beat `ChapterRef` / `SceneRef` free-text fields may later gain resolvers; they are not a second scene store.

## 5. Associating scene prose with a scene (chapter Markdown preserved)

### Approaches compared

| Approach | Idea | Pros | Cons |
|----------|------|------|------|
| **A. In-chapter delimiters (recommended)** | Scene prose is a contiguous region inside the chapter `.md`, bounded by stable HTML comments carrying `Scene.Id` | Keeps chapter files as compile unit; matches architecture rule; snapshots/journal already cover chapter files; unstructured chapters keep working | Needs careful rewrite on split/move; authors can damage markers in external editors |
| **B. Per-scene Markdown files** | `09 Draft/Scenes/{id}.md`; chapter file becomes include-list or assembly | Clean per-scene I/O | Breaks “chapter Markdown is the manuscript”; dual compile path; larger migration |
| **C. Prose in SQLite** | `Scene.Body` TEXT | Simple transactions | Violates PRODUCT_SPEC §6 (large prose out of DB); hurts Recovery/export patterns already built around files |

### Recommendation: **Approach A — in-chapter scene delimiters**

**Marker format (opaque to preview; stripped or ignored by Markdig as HTML comments):**

```markdown
<!-- mbws:scene id="{guid}" -->
…scene prose…
<!-- /mbws:scene -->
```

**Rules**

1. Chapter file remains the sole compile/export prose source for that chapter.
2. Assigned scenes may each own at most one span in their chapter file.
3. **Backward compatibility:** Chapters with **no** markers are valid forever. Entire file body is chapter prose; linked scenes stay outline-only until the author runs “Insert scene break” / split, which wraps regions. No forced rewrite on migrate.
4. Unassigned scenes have **no** file span; assigning a scene to a chapter appends an empty delimited region (or inserts at drop index) without inventing duplicate outline rows.
5. Scene `WordCount` / `LastEditedUtc` update when the span (or whole chapter if editing undifferentiated prose) is saved.
6. External edits that remove markers: on load, treat as unstructured chapter; scenes remain in DB; UI offers “Re-link spans…” only if needed (Prompt 4+), never auto-deletes scenes.

**Why A over B/C:** Least disruption to `ChapterFileStore`, compile streaming, DOCX export, v1.1 journal entity `ManuscriptChapter`, and portable project layout.

## 6. Transaction and failure boundaries (SQLite + Markdown)

Cross-store operations cannot be one atomic distributed transaction. Use **ordered steps + journal + idempotent cleanup**.

### Pattern for metadata-only commands (reorder part/chapter/scene ids)

1. Open EF context; mutate rows; `SaveChangesAsync` in one SQLite transaction.  
2. On failure: nothing written; UI shows error.  
3. No Markdown touch.

### Pattern for chapter prose save (existing, keep)

1. Upsert recovery journal (`ManuscriptChapter`) with latest text.  
2. Atomic temp+rename write via `ChapterFileStore`.  
3. Update word count / hash in SQLite transaction.  
4. Clear journal on success; leave journal on failure.

### Pattern for commands that change DB **and** Markdown (assign/move scene, split/merge, delete scene unwrap)

1. **Pre-op safety snapshot** when the operation is structural (split/merge/move across chapters) — reuse `SafetySnapshotReason` (extend enum if needed).  
2. Journal the **target chapter file(s)** full text (and source chapter if moving).  
3. Apply Markdown rewrite in memory → atomic write each file.  
4. Commit SQLite metadata in one transaction (chapter ids, sequences, scene rows).  
5. Clear journals on full success.  
6. **On failure after partial file write:** do not clear journals; prefer Recovery Centre; avoid deleting the only good copy. If DB committed but file failed, journal holds file truth for recover-to-copy; Prompt 1–2 tests must define “DB first vs file first” — **recommendation: write files first (journaled), then DB**, so DB never points at spans that never landed. If DB fails after file write, file is still valid UTF-8; next load reparses markers.

### Delete chapter

Keep today’s order: unlink scenes in DB → remove chapter row → delete file → renumber. Strengthen with journal/snapshot for the deleted file content when Prompt 2 implements hierarchy deletes (material risk if file deleted before durable journal).

## 7. How v1.1 safety systems protect new operations

| System | Protection for v1.2 ops |
|--------|-------------------------|
| **Snapshots** | Safety snapshot before migrate (schema v8), compile/export, and structural split/merge/move; retention/retire unchanged |
| **Atomic chapter writes** | All delimiter rewrites go through `AtomicFileWriter` / `ChapterFileStore` |
| **Crash journal** | Extend usage so structural edits journal chapter markdown before rewrite; scene outline field edits should join document-style journaling or a dedicated `SceneMetadata` journal type in Prompt 4 (outline-only updates can stay DB-transactional without journal if no file touch) |
| **Autosave** | Manuscript editor continues debounced chapter saves; corkboard title/status edits debounce to `UpdateSceneAsync`; switching hierarchy nodes flushes pending saves (same as chapter switch today) |
| **Undo/redo** | Prose: native TextBox stack; rebases on chapter/scene-focus change. Structural hierarchy ops: **not** on the text undo stack — use explicit Undo via model command history **or** rely on snapshot/restore for large ops (recommend bounded `HierarchyEditHistory` in Prompt 2–3, max 100, parallel to document undo) |
| **Diagnostic sanitizer** | Continues to redact manuscript/journal payloads from Recovery notes |

## 8. Planned EF migrations and safe backfill from schema v7

**Current:** `ProjectSchema.CurrentVersion = 7` (migrations through `AddPostPublicationTracking`).

### Migration plan → schema **v8** (single EF migration preferred; split only if SQLite limits force it)

**Name (illustrative):** `AddManuscriptHierarchyPartsAndSceneOrder`

| Change | Detail |
|--------|--------|
| `Parts` table | `Id`, `ProjectId`, `SequenceNumber`, `Title`, `LastEditedUtc?`; unique `(ProjectId, SequenceNumber)`; FK → `Projects` cascade |
| `Chapters.PartId` | Nullable `Guid?`; index `(ProjectId, PartId)`; FK → `Parts` **SetNull** on part delete |
| `Scenes.ChapterId` | Add optional EF FK → `Chapters` **SetNull** on chapter delete (matches app behaviour) |
| Scene uniqueness | Drop project-wide unique `(ProjectId, SequenceNumber)` on Scenes; add filtered unique indexes: assigned `(ChapterId, SequenceNumber)` WHERE ChapterId NOT NULL; unassigned `(ProjectId, SequenceNumber)` WHERE ChapterId IS NULL (SQLite filtered indexes via raw SQL in migration if EF limited) |
| `SchemaVersions` / app constant | Bump `ProjectSchema.CurrentVersion` to **8** in the implementation prompt that lands the migration |

### Backfill (run in migration or immediately after in same open transaction)

1. Create **no** default Part rows (avoids surprising structure). All existing chapters: `PartId = null`.  
2. For each project, partition scenes by `ChapterId`. Within each chapter group, renumber `SequenceNumber` to dense 1..n ordered by old sequence then title.  
3. Renumber unassigned scenes similarly within the unassigned partition.  
4. Orphan `ChapterId` values that do not match a chapter → set null (data repair).  
5. Do **not** rewrite any Markdown files in this migration.  
6. Open path already takes a **safety snapshot when migrations are pending** — keep that gate.

### Forward compatibility

- Export JSON `schemaVersion` follows `ProjectSchema.CurrentVersion`.  
- Older app builds must not open v8 projects (existing migrate-on-open pattern assumes newer app).

## Material risks for Prompt 1

1. **Scene unique index change** — Today `(ProjectId, SequenceNumber)` is unique for all scenes. Backfill must renumber **per chapter / unassigned partition** before dropping the old index, or migration fails on real projects with reused sequences across chapters.  
2. **Orphan `ChapterId` values** — Soft links may already point at deleted chapters; backfill must null them before adding FK.  
3. **Filtered unique indexes on SQLite** — May need raw SQL in the EF migration; must be covered by migration tests on a copied v7 database fixture.  
4. **Scope creep** — Prompt 1 must **not** rewrite Markdown, add corkboard, or bump app version; keep blast radius to schema + domain + tests.  
5. **Compile order semantics** — Introducing Parts without clarifying ungrouped-chapter ordering could change export order; Prompt 1 helpers must freeze the rule in §2–3 with unit tests before UI exists.

---

## Design decisions locked by this audit

1. Preserve **chapter UTF-8 Markdown files** as the manuscript/compile source of truth.  
2. Preserve **one canonical Scene inventory** projected everywhere.  
3. Add **Parts** as optional grouping; null `PartId` is valid.  
4. Associate scene prose via **in-chapter delimiters**, with full backward compatibility for unmarked files.  
5. Deliver v1.2 through **seven dependency-ordered prompts** above; Prompt 1 is schema/domain only.
